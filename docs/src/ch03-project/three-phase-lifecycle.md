# The Three-Phase Modification Lifecycle

Sovereign concept chapter: the three phases a modification passes through —
in-memory format, disk post-hook, and mandatory verification — and why their order
is not negotiable.

A change set is not written to disk and then repaired. It is formatted while it still
lives in virtual staging, side effects run only after it reaches disk, and
verification runs only after those side effects finish. Each phase has one job, one
moment, and one failure contract. Orthogonal to all three is the question of how
the change set addresses the lines it replaces: one strategy profile answers it,
and a rejected change set is explained in the same vocabulary.

---

## 1. Motivation & Invariants ("Why")

### 1.1 A modification is not one write

Three different concerns surround a change set:

- its **shape**, which a formatter can improve without knowing the task;
- its **consequences on disk**, which a code generator, a lock-file refresh, or a
  migration must produce;
- its **correctness**, which only a compiler, a linter, or a test suite can judge.

Collapsing them into one step forces a bad compromise. Formatting after the write
creates diffs nobody proposed. Running a generator before the write reads stale
input. Verifying before the generator runs checks a tree that is not final.

### 1.2 Why the order is fixed

1. **Format before disk.** The staged content is the real payload. Rewriting it in
   memory keeps the proposed change coherent and prevents a formatter from changing
   bytes staging never validated.
2. **Post-hook after disk, before verification.** Generated sources, refreshed lock
   files, and migrations must exist when verification runs. Running a hook before the
   write would generate from the previous content.
3. **Verification after both.** The verification command must see the final tree:
   formatted input, applied patch, completed side effects.

### 1.3 The invariants

1. **In-memory format touches no disk.** The filter receives content on standard
   input and returns content on standard output.
2. **An unclaimed or failed format keeps the authored content.** Formatting is
   best-effort and never blocks a turn.
3. **Formatting is a single in-memory pass.** There is no disk formatting stage, so a
   formatter can never rewrite a verified tree.
4. **Post-hooks run strictly after the write and before verification.**
5. **Post-hook artifacts join the same change set.** They are captured through Git
   with `.gitignore` respected, so verification and the final atomic commit see them.
6. **A failed post-hook aborts the change set.** A tree whose generator failed cannot
   be committed.
7. **Verification is declared and mandatory.** A change set the harness cannot verify
   is never accepted, and a failing command yields typed diagnostics rather than a
   transcript.
8. **Routing is declarative.** The declaration decides which command owns a phase;
   the engine never hardcodes a language, and a phase that does not apply is skipped,
   not faked.
9. **A path the repository ignore rules exclude is rejected before the write.** A
   patch that would create, overwrite, or move onto such a path fails during
   in-memory staging, before any byte reaches disk and before Git is asked to stage
   it. Post-hook artifacts are exempt, because they are discovered through a Git
   differential that honors the same rules.
10. **Artifacts produced during verification join the change set.** The working copy
    is baselined once, when the first change set reaches disk. After a clean
    verification the harness reads the differential against that baseline, so a lock
    file refreshed or a snapshot regenerated by the toolchain enters the same atomic
    commit instead of surviving as untracked residue.
11. **An anchored change set is resolved before the write.** When the declared patch
    strategy names lines by opaque anchors, every range is validated against one
    snapshot of the file — inside the file, never running backwards, never sharing a
    line with another range — and the validated ranges are applied from the bottom of
    the file upwards. Anchors change how a change set *addresses* its lines, never
    when or how it is formatted, hooked, or verified.
12. **Strategy vocabulary has one owner.** The fields that address a range, the
    schema descriptions, the prompt instructions that name them, the retry
    guidance, and the strategy-dependent diagnostics are read from one strategy
    profile, so no consumer restates them and no two surfaces can disagree about
    what a change entry carries.

## 2. Mental Model & Ontology ("What")

### 2.1 The phases

| Phase | Declared by | Channel | Moment | Failure contract |
| --- | --- | --- | --- | --- |
| **In-Memory Format** | `[project.format]`, or the `format` recipe the declared task runner exports | standard input and output | before any byte reaches disk | the authored content is kept |
| **Disk Post-Hook** | `[project.post_hook]` | a plain process | after the write, before verification | the change set is aborted |
| **Verify** | `[project.verify]` | a plain process | after every phase above | typed diagnostics feed the healing loop |

### 2.2 Terms

- **Staged content** — the validated in-memory text a change set will write.
- **In-memory format** — rewriting staged text through the declared stream filter.
- **Disk post-hook** — a side effect that needs the file to exist on disk.
- **Verification command** — the mandatory command that decides whether the change
  set is accepted.
- **Change set** — the repository-relative paths the turn produced: the patch, the
  post-hook artifacts, the writes a repair round left behind, and the paths the
  verification command rewrote while it checked the tree.
- **Worktree baseline** — the working-copy snapshot taken once, immediately after the
  first change set reached disk. The differential against it is what turns an
  unreported write by the toolchain into a member of the change set.
- **Opaque line anchor** — a compact four-symbol token naming exactly one line of a
  file rendered in the context block. It is a permutation of the line index seeded
  by the file's repository path rather than a counter, so it has to be copied from
  the file's own block instead of computed or reused across files.
- **Anchored change set** — a change set whose ranges are named by a pair of anchors
  instead of by the text they replace.
- **Strategy profile** — the single declaration of everything a strategy
  contributes: the fields that address a replaced range, the schema descriptions
  and prompt instructions that name them, the contract invariant of a
  replacement, and the wording of its diagnostics.

### 2.3 Exactly one formatting surface

Formatting has a single contour: the declared `[project.format]` filter rewrites
staged content on its way from virtual staging to disk. There is no second pass over
the working tree, so a formatter can never introduce a diff the turn did not propose,
and no compensation layer has to restore verified content afterwards.

### 2.4 The change set is the single truth of a turn

Verification, the final commit, and the reported result all read one list. It is
built from three sources: the paths the patch wrote, the artifacts the post-hook
produced, and the paths a failed repair left dirty in the working copy. Merging them
into one ordered, duplicate-free list is what prevents a file that is visibly
modified on disk from falling outside the commit that claims to describe the turn.

The list is completed by a single baseline. The working copy is snapshotted once,
immediately after the first change set reaches disk and before verification starts.
A successful verification then compares the working copy against that baseline
through Git, so the paths the toolchain rewrote while it checked the tree — a
refreshed lock file, a regenerated snapshot, an artifact a test harness produced —
join the change set exactly like a repair-round write. The baseline is captured once
on purpose: a differential that advanced with every healing round would silently drop
an artifact produced by an earlier one.

A path the repository ignore rules exclude enters no source at all. A patch that
would create, overwrite, or move onto such a path is rejected while the change set
still lives in memory, so Git is never asked to stage a file the harness already
wrote. Post-hook artifacts obey the opposite rule on purpose: they are discovered
through a Git differential that honors the same ignore rules, so a generated build
file is simply absent from the change set instead of aborting it. Responsibility is
split accordingly — model-generated code may only target tracked paths, while a
declared external generator may produce ignored output without failing the turn.

### 2.5 Addressing a range: echoed text or anchors

A change set has to say *which* lines it replaces. Two strategies exist, and the
project declares one of them in `[develop] patch_strategy`:

| Strategy | A range is addressed by | Cost of one range |
| --- | --- | --- |
| `search_replace` | the replaced lines, echoed verbatim and matched exactly | every replaced line is paid for twice: once in the prompt, once in the proposal |
| `line_anchor` | the opaque anchors rendered beside the first and last replaced line | two four-symbol tokens, however much text the range holds |

The strategy is orthogonal to the transport. Whether the model speaks marker-tagged
XML or Structured Output JSON, the same two strategies are available: the transport
decides the encoding of a change, the strategy decides the fields that address its
range.

An anchor is a permutation of the line index seeded by the file's repository
path, not a counter. Neighbouring lines produce unrelated tokens, and the same
line of two files carries unrelated tokens too, so the model cannot count its
way to a line and has to copy the token from the context block of the very file
it edits. Resolution happens during in-memory staging,
before formatting and before any byte reaches disk: every range is validated
against one snapshot of the file, and the validated ranges are applied from the
bottom of the file upwards, so replacing a lower range never moves the lines a
higher range already named.
higher range already named.

### 2.6 One owner for the strategy vocabulary

Everything a strategy contributes lives in one module,
`crates/core/src/edits/strategy.rs`: the fields of a change entry that address the
replaced lines, the description the wire schema publishes for them and for
`content`, the XML and structured instructions the prompt renders, the contract
invariant of a replacement, the guidance for fields that do not apply, the
correction guidance of a retry, and the wording of the two rejections that carry
strategy vocabulary — a replacement that matched nothing and a range addressed
more than once.

A profile is pure data plus one rendering function per contour. It reads no file,
keeps no state, and produces identical text for identical input, so prompt
assembly, the wire schema, and the diagnostics of a failed patch read one
declaration instead of restating its terms.

The retry contour is where that ownership pays for itself. The retry request and
the retrying event receive the active strategy explicitly and render their reasons
and their correction guidance from the profile, so a `line_anchor` turn is never
asked to echo the text it replaces and a `search_replace` turn is never told to
copy an anchor. A report written in another dialect would teach the model a field
the prompt never mentioned: the model would send it, staging would reject it with
an ambiguity the model cannot explain, and the turn would spend a round repairing
a defect the harness introduced.

A rejection that carries no strategy vocabulary keeps its own wording under every
strategy. An ignored path or a file that does not exist is reported identically,
because rewording it would add a distinction the failure does not have.

### 2.7 Adding a strategy

A third strategy is a delimited change:

1. add a variant to `PatchStrategy` in `crates/protocol`;
2. add one entry to the profile module — `StrategyProfile::of` matches
   exhaustively and every field of a profile is mandatory, so a strategy without
   a profile, or with a partially described one, does not compile;
3. extend the contract tests, which assert that each strategy's texts name only
   its own vocabulary.

The first two points are what keep the vocabulary from spreading. No consumer
restates a field name, an invariant, or a diagnostic, so there is no second place
to update and no place where a stale paraphrase survives compilation.

## 3. Mechanics & Lifecycle ("How it behaves")

### 3.1 In-memory format

Staged text is authored by the change set, and under the `line_anchor` strategy that
authoring starts with resolution rather than with text: every named range is
validated against the snapshot the context block rendered and applied from the
bottom upwards, so the staged content is the file with its ranges replaced.
Formatting then rewrites that content exactly as it rewrites an echoed one — the
two strategies differ in how a range is addressed, never in what happens to the
result.

The harness resolves the single formatting surface — the declared `[project.format]`
entry, or the `format` recipe the declared task runner exports when that entry is
omitted — and streams one file's staged content through it. The declaration owns the
arguments, the harness owns the stream, and the child runs in its own process group,
so a filter that spawns a helper cannot outlive the phase.

The outcome distinguishes an absent declaration, a rewritten file, and a failure:
a non-zero exit status, a timeout, or a cancellation keeps the authored content and
reports why. Because the filter reads a stream and writes a stream, it cannot create,
delete, or rename anything in the working tree.

### 3.2 Disk post-hook

Once the change set is written, the declared post-hook runs as a plain process. It
receives the literal arguments its declaration names and no file list: the harness
does not guess which paths the generator needs, and the hook does not have to parse a
request to learn them.

The working copy is snapshotted before the hook starts and after it exits
successfully, and the difference — computed through Git, with ignores respected —
becomes part of the turn's change set. A hook that fails, times out, or is cancelled
aborts the change set: the caller reports a failed generator instead of committing
artifacts nobody can reproduce.

### 3.3 Verification

Verification runs the declared `[project.verify]` command with its own wall-clock
budget and stops at the first failure, because a later command would run on top of a
change set the earlier one already rejected. Cancellation stops the pipeline
immediately and rolls the turn back.

A failing command's combined output is parsed into typed diagnostics — file, line,
column, severity, code, and message — and those diagnostics are what enters the
healing loop. The transcript never does. A repository with nothing to build verifies
cleanly with no steps, so the gate does not fail a project that has nothing to
compile.

### 3.4 Verification artifacts

The verification command runs on the real tree, and a package manager refreshing a
lock file or a test harness regenerating a snapshot writes into that tree while it
checks it. The check is therefore followed by one deterministic read: the working
copy is compared against the baseline captured when the change set reached disk, and
every differing path joins the change set before the commit is created.

The consequence is a closed bookkeeping loop. A turn whose verification rewrote a
file commits that file, the reported change set matches what the commit contains, and
the working copy is clean once the turn ends. Paths excluded by the repository ignore
rules stay outside the differential exactly as they stay outside the post-hook one,
so a generated build artifact neither joins the commit nor blocks it.

### 3.5 Targets

A verification request names a target: all, check, test, or lint. The declared
`[project.verify]` command is authoritative for every target, because the repository
described its own lifecycle; the target is a label for the interface, never a command
selector.

There is no legacy resolution and no manifest auto-detection. A repository that
declares no verification command resolves no step, so the change set is reported as
unverified instead of running a command nobody declared.

### 3.6 Failure semantics

- **Ignored path** — a patch targeting a path the repository ignore rules exclude
  is rejected during in-memory staging with a typed diagnostic, so the model can
  choose a tracked path within the same turn instead of aborting it.
- **Invalid or overlapping anchored ranges** — a range that names a malformed
  token, a line outside the file, a backwards span, or a line another range of the
  same change set already addresses is rejected during in-memory staging. The
  diagnostic names the file, the anchor, and the file's line count, so the model
  repairs the range within the turn instead of aborting it.
- **Format failure** — the authored content is kept and the turn continues.
- **No declared formatter** — the file is written exactly as authored; this is the
  normal outcome for documentation and configuration.
- **Post-hook failure** — the change set is aborted and the turn fails with the
  hook's diagnostic instead of a misleading compile error.
- **Verification failure** — the diagnostics enter the healing loop; nothing is
  committed until verification passes, and the files the failed command wrote are
  rolled back with the rest of the tree.
- **Cancellation** — a cancelled phase stops immediately; an interrupted turn rolls
  the working tree back instead of committing a partially processed tree.
- **Strategy-aware retry** — a replacement that matched nothing, a range addressed
  more than once, and an anchor that lies outside the file are explained in the
  dialect of the active strategy, so the repair request names the addresses the
  turn actually sent.

### 3.7 Timeouts and process isolation

Every phase is one invocation with a wall-clock budget, an isolated process group, and
a teardown that reaps the child. A formatter that spawns a compiler, a hook that spawns
a generator, and a verification command that spawns a test binary are torn down together
when the budget expires or the developer cancels.

## 4. Boundaries & Anti-Patterns ("What it is NOT")

- **It is not a shell pipeline.** Every phase declares an executable and literal
  arguments; nothing is interpreted by a shell.
- **It is not a single pass.** Formatting, side effects, and verification have
  different inputs and different moments.
- **It is not unconditional.** A repository declares which phases exist; a missing
  declaration means the phase is skipped rather than faked.
- **It is not a formatter-only protocol.** A project with no formatter still has a
  post-hook and a verification command.
- **It is not a replacement for verification.** Formatting cannot prove correctness,
  and a formatted file is not a verified file.
- **It is not a hidden rewrite.** In-memory output still travels through staging and
  the normal commit path, so the formatted bytes are exactly the bytes the turn
  proposed.
- **It is not a text-echo protocol.** A change set may name its ranges by anchors
  instead of echoing them; formatting, hooks, verification, and the commit treat the
  resolved content identically.
- **It is not a prompt-only setting.** The strategy travels as a typed parameter
  into the wire schema, the prompt, the retry request, and the diagnostics, so no
  consumer infers it from text it was parsing or from the shape of a change set it
  received.
- **It is not a post-verification disk pass.** Formatting runs once, before the
  change set reaches disk; nothing reformats a verified tree afterwards, so no
  compensation layer has to restore it.
- **It is not an escape hatch around ignore rules.** A path the repository ignore
  rules exclude cannot enter the change set through the patch; generated artifacts
  reach it only when Git does not consider them ignored.
- **It is not language-specific.** The engine names paths and declared commands; it
  never names a compiler.
- **It is not a best-effort commit of a failed generator.** A failed post-hook ends
  the change set.
- **It is not a commit of the proposal alone.** A path the turn produced — during the
  post-hook, during a repair round, or during verification — is committed even when
  the model never wrote it, because the change set is read off the tree, not off the
  proposal.
