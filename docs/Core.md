# Core

## 1. Назначение

Core (`tauqe-core`) — независимое от интерфейса ядро системы. Его назначение — **делать работу**.

Core ничего не знает о TUI, Emacs, графических интерфейсах, терминальных виджетах или горячих клавишах.

Архитектурным ориентиром разделения обязанностей выступает **SLIME (Swank)**: ядро и сервер живут как независимый рантайм, хранящий сессионное состояние проекта, а клиенты подключаются к нему по строгому семантическому протоколу.

## 2. Архитектурная граница и структура воркспейса

Реальная структура Rust-воркспейса:

```text
crates/
  core/        # Ядро: Git, контекст, протоколы правок, история, воркфлоу, LLM-клиент
  protocol/    # Типы JSON-RPC протокола, методы, события и контракты
  server/      # Диспетчер протокола, работающий через stdio
  tui/         # Терминальный клиент на базе Ratatui/Crossterm
```

Ключевой инвариант:

> TUI не зависит от `tauqe-core` напрямую. TUI является клиентом `tauqe-protocol`.

## 3. Доменная модель

Фактические сущности системы:

```text
RepositoryState        # Снимок Git: корень, ветка, HEAD, dirty-статус
ContextManager         # Управление файлами контекста (Editable / ReadOnly)
ContextItem            # Метаданные файла контекста (токены, размер, доступ)
CheckpointInfo         # Временный коммит dirty-состояния разработчика
EditOperation          # Атомарная операция: Replace, Create, Delete
EditProposal           # Набор правок с кратким саммари
StagedEditsState       # In-memory состояние файлов до записи на диск
HistoryManager         # Персистентная семантическая история в JSONL
HistoryEntry           # Записи истории: Summary, Turn, Response, Undo
EditProtocol           # Трейт формата правок (XmlEditProtocol, StructuredEditProtocol)
EditWorkflow           # Трейт сценария исполнения (Toolchain, Git, Naive)
```

## 4. Репозиторий и Git-подсистема

Git-репозиторий является единственным источником правды о состоянии кода.

Core умеет:
- определять repository root, HEAD, branch, status, diff;
- защищать незакоммиченные изменения разработчика через checkpoints;
- создавать изолированные AI-коммиты с явным авторством `Tauqe AI <ai@tauqe.dev>`;
- выполнять детерминированный откат изменений (`undo`).

### 4.1 Защита dirty changes через Checkpoints
Перед применением правок модели ядро создаёт чекпоинт (`create_checkpoint`):
- Если в рабочем дереве есть незакоммиченные изменения разработчика, они временно коммитятся в изолированный коммит `tauqe-checkpoint: uncommitted user changes`.
- После успешного применения правок создаётся целевой коммит `Tauqe AI` с кратким саммари.
- Пользовательские и модельные правки никогда не слипаются в один неразделимый diff.

### 4.2 Детерминированный Undo
Undo выполняется детерминированно через Git:
- Проверяется, что коммит в `HEAD` действительно создан `Tauqe AI`. Если коммит пользовательский — операция безопасно отклоняется.
- Выполняется `git reset --hard HEAD~1`.
- Если перед AI-коммитом был создан чекпоинт пользователя, выполняется смешанный откат чекпоинта (`git reset HEAD~1`), возвращающий исходные незакоммиченные файлы разработчика в рабочее дерево без потерь.

## 5. Рабочие процессы редактирования (Workflows)

Ядро поддерживает подключаемые стратегии выполнения задач (`EditWorkflow`):

1. **`toolchain` (по умолчанию):**
   - **Patch Retry Loop:** пофайловая in-memory валидация сопоставлений search/replace, кумулятивное сохранение сошедшихся файлов и автоматический точечный перезапрос только сбойных файлов (до `max_retries` попыток) до записи на диск.
   - Создаёт чекпоинт пользовательских изменений.
   - Атомарно применяет проверенные правки к файловой системе.
   - Запускает проектную проверку (`cargo check` для Rust; `npm test` / `tsc` для TypeScript).
   - **Auto-healing feedback loop:** в случае ошибок компиляции ошибки перехватываются и передаются обратно модели в диалог для автоматического исправления.
   - При успехе проверки фиксирует изолированный AI-коммит.
   - При исчерпании попыток — безопасно откатывает рабочее дерево к исходному чекпоинту, гарантируя, что код проекта не останется в сломанном состоянии.
2. **`git`:**
   - Patch Retry Loop → чекпоинт незакоммиченных изменений → атомарное применение правок → изолированный AI-коммит без вызова тулчейна.
3. **`naive`:**
   - Patch Retry Loop → простое атомарное применение правок к файловой системе без создания Git-коммитов.

Смена workflow блокируется во время активной генерации модели.

## 6. Протоколы взаимодействия и модификации кода (Edit Protocols)

Ядро абстрагирует формат взаимодействия с моделью через фабрику `EditProtocol`:

1. **`xml` (по умолчанию):**
   - Структурированный XML-протокол тегов `<tauqe_edits>`, `<edit>`, `<create>`, `<delete>`, `<search>`, `<replace>`.
   - Потоковая фильтрация и валидация единственности сопоставления (`Search/Replace`) на сервере в реальном времени.
   - Поддерживает свободный текст и рассуждения модели (reasoning) до и между тегами.
   - Создание и полная перезапись файлов покрываются тегом `<create path="...">`.
2. **`structured`:**
   - Строгий JSON Schema (Structured Output), задающий контракт `ModelResultProposal` (`message`, `changes`, `context_requests`, `suggested_actions`).
   - Потоковый парсинг через конечный автомат `struson` без ожидания полного завершения ответа.

Смена протокола блокируется во время активной генерации модели.

## 7. Поддерживаемые экосистемы (Rust & TypeScript)

Целевой фокус системы строго ограничен двумя экосистемами:
1. **Rust (основная экосистема разработки):**
   - Детекция `Cargo.toml`.
   - Проверочная команда по умолчанию: `cargo check`.
2. **TypeScript / JavaScript (перспектива развития):**
   - Детекция `package.json`, `tsconfig.json`.
   - Проверочные команды: `npm run check`, `npm run typecheck`, `npx tsc --noEmit`, `npm test`.

Другие экосистемы не рассматриваются.

## 8. Инвариант: arbitrary shell запрещён

> **У модели нет произвольного доступа к командной оболочке (shell).**

Модель не может выполнять произвольные команды ОС. Она может лишь предлагать правки в файлы и запускать предопределённую верификационную команду тулчейна в рамках активного воркфлоу.

## 9. Контекст: Knowledge Scope vs Write Scope

Контекст — первоклассное состояние:
- **Knowledge Scope:** файлы, доступные модели для чтения (`read_only` или `editable`).
- **Write Scope:** строго файлы с правами `editable`. Модель не имеет права предлагать изменения для `read_only` файлов.
- **Batch Pattern Add:** поддержка пакетного добавления файлов по glob-маскам и префиксам директорий (например, `crates/core/src/*.rs`).

## 10. Потоковая фильтрация и двухфазная валидация правок

Сервер реализует потоковый фильтр (`XmlStreamFilter` / `JsonStreamFilter`):
1. **Фаза 1 (Стриминг и валидация в памяти):**
   - Текст рассуждений и комментариев передаётся клиенту в реальном времени (`model/textDelta`, `model/reasoningDelta`).
   - Служебная разметка правок перехватывается и не попадает в текстовый поток клиента.
   - По мере закрытия каждого блока сервер отправляет семантические события (`edit/fileStarted`, `edit/hunk`, `edit/fileDone`).
   - Чанки валидируются в памяти на копии файла: если `search` не найден или неоднозначен, фиксируется ошибка валидации.
   - **Patch Retry Loop:** если часть файлов не сошлась (`NoMatch` или `AmbiguousMatch`), успешно сошедшиеся файлы сохраняются в памяти, а для сбойных файлов генерируется точечный промпт исправления и клиентам отправляется событие `edit/fileRetrying`. Цикл повторяется до `max_retries` раз исключительно в памяти.
2. **Фаза 2 (Атомарная транзакция на диск):**
   - Только если **все** правки всех файлов успешно прошли валидацию и модель завершила ответ, изменения атомарно записываются на диск (`apply_edit_proposal`).
   - Обновляются метаданные в `ContextManager`.
   - Если хотя бы один файл содержит ошибку и исчерпаны попытки восстановления — диск остаётся нетронутым, частично применённых правок не возникает.

## 11. Семантическая история взаимодействия

Вместо раздувающегося текстового чата ядро ведёт структурированную историю:
- Реальные изменения кода фиксируются в Git; в истории сохраняется только пояснение модели, хеш созданного AI-коммита и список затронутых файлов с префиксами `[NEW]`, `[EDIT]`, `[DEL]`.
- Для каждого хода пользователя сохраняется состав путей контекста на момент отправки.
- Операции создания коммитов и отката (`undo`) логируются как первоклассные события.
- История сохраняется в едином файле `.tauqe/history.jsonl` в формате JSON Lines.
- При превышении лимита токенов старая часть истории автоматически сжимается в единый `summary`, а последние детальные шаги сохраняются в хвосте диалога.

## 12. Golden rules

> **Git defines reality.**

> **Context defines what the model knows.**

> **Permissions define what the model may change.**

> **The agent has no arbitrary shell.**

> **Never ask the model a question the environment can answer deterministically.**

> **The application owns state; the model performs semantic work inside strictly enforced boundaries.**
