# Семантическая история взаимодействия и компактификация (Semantic Interaction History)

## 1. Назначение и концепция

В отличие от традиционных LLM-интерфейсов, сохраняющих бесконечный плоский лог текстовых сообщений, Workbench рассматривает взаимодействие с моделью как **цепочку семантических шагов (Semantic Turns)**.

### Ключевые архитектурные принципы:
1. **Git defines reality:** В истории диалога не сохраняются исходные diff'ы, чанки search/replace или сырые XML-блоки. Реальный код изменений уже хранится в Git-репозитории. Дублирование diff'ов в истории приводит к лавинообразному переполнению контекстного окна модели.
2. **Семантическое сжатие ходов (Turn Compaction):** Ответ модели фиксируется как компактный результат: свободный текст пояснения + метаданные коммита + список затронутых файлов.
3. **Контекстный снимок (Context Snapshot):** Для каждого пользовательского запроса сохраняется снимок файлов, находившихся в контексте в момент отправки запроса.
4. **Git-события как первоклассные сущности диалога:** Фиксация AI-коммитов и их последующий откат (`undo`) записываются в журнал сессии, благодаря чему модель точно понимает, почему код вернулся к предыдущему состоянию.
5. **Идентичность «диск — промпт»:** Содержимое файла сессии в формате JSON Lines передается модели в промпт напрямую внутри тега `<history>` без какой-либо промежуточной переконвертации в другие форматы.

---

## 2. Структура семантического хода

На один пользовательский промпт модель может отвечать несколькими семантическими шагами (например: генерация правок → ошибка компиляции тулчейна → автоматическое исправление → финальный ответ).

### Доменная модель

```text
UserTurn
├── id / timestamp
├── prompt (текст намерения разработчика)
├── context_snapshot (список файлов и режимы доступа: read_only / editable)
└── responses: Vec<SemanticResponse>
    ├── Answer { message }
    ├── EditApplied { message, commit_hash, summary, touched_files: Vec<(path, op)> }
    ├── ToolchainResult { command, success }
    └── GitEvent { event: commit | undo | squash, commit_hash, ... }
```

## 3. Формат персистентного хранения: JSON Lines (`.jsonl`)

История сохраняется в служебной директории проекта `.workbench/` в едином файле:

```text
.workbench/
  history.jsonl          # Единая сессия взаимодействия для репозитория
```

Директория `.workbench/` включается в `.gitignore`.

### Формат строк (JSONL)

Каждая строка представляет собой валидный компактный JSON-объект с полем `type`:

```json
{"type": "summary", "text": "Реализован потоковый XML-парсер, настроена потоковая валидация в памяти."}
{"type": "turn", "prompt": "Добавь обработку тега delete", "context": ["crates/core/src/edits.rs"]}
{"type": "response", "message": "Добавил поддержку тега delete в парсер", "commit": "a1b2c3d", "summary": "Support delete tag in XML parser", "files": ["crates/core/src/edits.rs"]}
{"type": "undo", "commit": "a1b2c3d", "restored_checkpoint": true}
```

*Преимущества:*
- **Append-only:** новые события безопасно дописываются в конец файла без риска повредить предыдущую историю при сбоях.
- **Прозрачность:** файлы легко читаются стандартными утилитами (`cat`, `jq`).
- **Легковесность:** отсутствие внешних баз данных; работа через стандартный `serde_json`.

## 4. Логирование откатов (Undo) и сквоша (Squash)

### 4.1 Логирование Undo
При выполнении детерминированного отката (`git/undo` в ядре или по клавише `u` в TUI):
- В журнал текущей сессии дописывается событие `undo` с указанием хеша отмененного коммита.
- При последующем запросе модель видит в истории событие отката, что предотвращает галлюцинации и повторение уже отвергнутых решений.

### 4.2 Перспектива: Интерактивный сквош коммитов (Squash)
При сжатии цепочки AI-коммитов в один целевой коммит:
- Серия промежуточных микро-шагов в истории объединяется.
- Сквош коммитов в Git служит естественным триггером для суммаризации соответствующего фрагмента сессии.

## 5. Механизм компактификации (Суммаризация)

С течением времени семантическая история начинает превышать лимиты контекстного окна LLM.
Для контроля объема используется механизм компактификации на основе **estimated tokens** (или объема символов/байт).

### 5.1 Пороговые значения (Token Budgeting)
- **Лимит истории (`History Limit`):** например, ~8 000 estimated tokens.
- **Целевой размер хвоста (`Tail Size`):** последние 2–3 полных хода (~3 000 tokens).
- **Лимит суммарного базиса (`Summary Budget`):** до 1 000 tokens.

### 5.2 Алгоритм сжатия
1. При добавлении нового хода ядро оценивает суммарный объем активной истории.
2. Если порог превышен:
   - Последние $N$ строк (хвост) остаются в детальном виде.
   - Голова истории (все предыдущие строки событий и предшествующий базис summary) отправляется на суммаризацию (через дешевую модель).
   - Сформированное резюме формирует новую строку `{"type": "summary", "text": "..."}`.
   - Файл `.jsonl` атомарно перезаписывается: первой строкой идет обновленный `summary`, далее — сохраненные строки хвоста.

## 6. Инжекция истории в промпт модели

История транслируется модели напрямую из файла сессии путем обрамления содержимого `.jsonl` в тег `<history>`:

```xml
<history>
{"type":"summary","text":"Ранее: реализован потоковый XML-парсер, удален неиспользуемый протокол tool_call."}
{"type":"turn","prompt":"Добавь обработку тега delete в XmlStreamFilter","context":["crates/core/src/edits/stream.rs"]}
{"type":"response","message":"Добавил поддержку тега delete в парсер.","commit":"a1b2c3d","files":["crates/core/src/edits/stream.rs"]}
{"type":"undo","commit":"a1b2c3d"}
</history>
```

### Преимущества прямой передачи JSONL в теге `<history>`:
1. **Отсутствие трансляторов:** исключен весь код преобразования JSONL → псевдо-XML → текст.
2. **Нативное понимание:** современные LLM обучались на гигантских корпусах JSONL и безупречно считывают хронологию событий из строковых JSON-объектов.
3. **Нет ограничений API на роли:** исключаются ошибки API-провайдеров при нарушении строгого чередования ролей `user` / `assistant` при системных событиях (`undo`, toolchain errors).
4. **Прозрачность отладки:** ровно то, что сохранено в `.workbench/history.jsonl`, передается модели.

---

## 7. Инварианты

1. **Никаких сырых diff'ов в истории:** история оперирует только хешами коммитов и списками затронутых путей.
2. **Детерминированность лога:** все критические действия (коммиты, откаты, изменения файлов) фиксируются строго по факту их реального завершения в Git и файловой системе.
3. **Единый журнал проекта:** семантическая история хранится централизованно в рамках репозитория без лишней сложности разделения по веткам.
4. **Один формат везде:** JSONL является форматом и для дискового хранилища, и для инжекции в контекст модели.
