* Overview
Цель плана — довести систему до состояния первичного самообеспечения (Bootstrap Point),
при котором дальнейшая разработка Workbench ведётся внутри самого Workbench.

План построен по принципу вертикальных проверяемых срезов: каждый этап даёт
запускаемый результат, который можно проверить вручную до перехода к следующему.

* Invariants & Constraints
- У модели нет произвольного доступа к shell. Доступны только зарегистрированные проектные действия.
- Git является единственным источником правды о состоянии репозитория и истории.
- TUI общается с ядром строго через протокол (никаких прямых зависимостей от workbench-core).
- Правки применяются детерминированно через атомарный Search/Replace (ровно одно совпадение old_text).
- Протокол взаимодействия строится по принципам SLIME/Swank (семантические события, presentation streams).

* DONE Этап 1. Живой каркас (Client + Server + Handshake)
- Суть этапа: Связывание TUI и Server через транспорт (stdio) по протоколу.
- Что можно проверить:
  - [X] TUI запускается и автоматически стартует Server как дочерний процесс.
  - [X] Клиент и сервер выполняют handshake (client/initialize).
  - [X] В интерфейсе TUI отображается верхняя панель: статус подключения, версия протокола, текущий репозиторий и ветка.

* DONE Этап 2. Диалог с моделью (Streaming, Reasoning & Cost Accounting)

- Что можно проверить:
  - [X] Наличие и загрузка файла конфигурации (TOML) с указанием API-ключа провайдера и выбранной модели по умолчанию.
  - [X] Ввод вопроса или задачи в поле ввода TUI.
  - [X] Потоковое отображение хода рассуждений (reasoning/thinking) и ответа в области Model Output в реальном времени. (Добавлено: автоматическое скрытие рассуждений при начале ответа, переключение по Ctrl+R).
  - [X] Извлечение данных об использовании (токены) и точной стоимости запроса (cost в USD) напрямую из ответа OpenRouter (включая фоновый опрос эндпоинта /generation).
  - [X] Отображение стоимости текущего ответа и суммарных расходов за сессию в интерфейсе TUI.
  - [X] Возможность прервать генерацию (Esc / Ctrl+C).
  - [X] Возможность очистить текущую историю разговора (Ctrl+L).
  - [X] Корректная обработка и отображение ошибок сервера в TUI (например, отсутствие API-ключа).

* DONE Этап 3. Контекст проекта (Файлы в контексте)
- Суть этапа: Отображение структуры контекста в TUI и учет файлов при формировании промпта для модели.
- Что можно проверить:
  - [X] В TUI отображается секция Context (Editable / Read-only).
  - [X] Пользователь может добавить файл из репозитория в контекст с режимом read-only (включая переключение на editable по «e» и удаление по «d»/«x»).
  - [X] Добавлена поддержка пакетного добавления файлов по glob-маскам и префиксам директорий (метод context/addPattern, фильтр в автокомплите пикера).
  - [X] Быстрое переключение между Model View и Context View по Ctrl+1 и Ctrl+2 с сохранением набранного текста запроса.
  - [X] TUI показывает оценку размера контекста (байты/токены) и ревизии.
  - [X] Модель отвечает на вопросы по добавленным файлам, опираясь на их актуальное содержимое через структурированный контекст.

* DONE Этап 4. Реальные правки файлов (XML-протокол, потоковая валидация и Org-Mode diff)
- Суть этапа: Переход от aider-маркеров к структурированному XML-протоколу редактирования, потоковый парсинг и валидация чанков в памяти сервера в реальном времени, отображение в стиле org-mode в TUI и атомарное применение на диск.
- Что можно проверить:
  - [X] Замена aider-маркеров на структурированный XML-протокол (<workbench_edits>, <edit>, <create>, <delete>, <search>, <replace>).
  - [X] Семантический потоковый фильтр на сервере (XmlStreamFilter): перехват тегов, очистка текста от служебной разметки, отправка событий edit/started, edit/fileStarted, edit/hunk, edit/fileDone, edit/finished.
  - [X] Потоковая валидация чанков в памяти сервера: проверка единственности совпадения search-блока в реальном времени.
  - [X] Двухфазность и атомарность: диск не затрагивается до полного завершения генерации; если хоть один чанк не сошёлся — все изменения безопасно отклоняются.
  - [X] Org-mode представление хода (turn) в TUI: компактный интерактивный список затронутых файлов со спиннерами ⠋ и статусами ✓ / ✗.
  - [X] Интерактивная навигация по правкам: перемещение по файлам ([ / ]), сворачивание и разворачивание unified diff по Space / Enter с цветовой подсветкой строк (+/-).
  - [X] Успешная модификация кода проекта самой средой (Self-Hosting: исправление подсчёта стоимости в openrouter.rs выполнено через Workbench).

* Этап 5. Интеграция Git (Чекпоинты, Diff и Undo)
- Суть этапа: Подключение Git-подсистемы ядра. Защита пользовательских незакоммиченных изменений и обратимость правок.
- Что можно проверить:
  - Перед применением правок модели ядро создаёт checkpoint для незакоммиченных изменений разработчика в целевых файлах.
  - После применения правок автоматически создаётся изолированный AI-коммит.
  - В секции Changes в TUI отображается diff применённых изменений.
  - Нажатие клавиши Undo откатывает изменения модели, полностью сохраняя локальные правки разработчика.

* Этап 6. Исполнение действий проекта и Evidence (Cargo Actions, Runs & Diagnostics)
- Суть этапа: Детектирование команд проекта без произвольного shell, сбор результатов и превращение ошибок в доказательства (Evidence).
- Что можно проверить:
  - Автоматическое обнаружение действий Cargo (check, test, clippy, fmt).
  - Запуск действия из TUI по горячей клавише (например, «c» для check).
  - Отображение результата прогона (PASS / FAIL) и логов в секции Runs.
  - При ошибке компиляции ошибки парсятся в структурированные Diagnostics и добавляются в контекст как Evidence.
  - Команда «исправь эти ошибки» передаёт структурированные ошибки модели для следующей итерации правок.

* Этап 7. Точка самообеспечения (Bootstrap Gate / Self-Hosting Loop)
- Суть этапа: Замыкание сквозного цикла разработки Workbench внутри самого Workbench.
- Что можно проверить:
  - Открытие репозитория Workbench в Workbench TUI.
  - Внесение намеренной ошибки компиляции или постановка задачи на добавление новой функции.
  - Запуск check -> получение FAIL -> добавление в Evidence -> запрос на исправление -> атомарное применение правки -> повторный запуск check -> PASS -> фиксация результата.
  - Дальнейшая разработка системы выполняется без использования внешних ассистентов.

* Post-Bootstrap Backlog (Stage 2)
- Декларативные профили сторонних экосистем (Node/TypeScript/pnpm, Python).
- Голосовой ввод (Voice Ingress, VAD, нормализация транскрипта и распознавание намерений).
- Семантический Repo Map на базе Tree-sitter и PageRank-ранжирование.
- Клиент для Emacs (workbench.el).
- Режим фонового демона (Unix Domain Socket) и одновременное подключение нескольких клиентов.
